# HealthConnect ML Engineering — Week 6 Issue Log

Tracks integration issues discovered and resolved during Week 6, per the
assignment's required deliverable. Each entry states what was found, how
it was found, and its current status — no issue here is asserted without
an executed test backing it.

| # | Issue | Discovered by | Severity | Status | Resolution |
|---|---|---|---|---|---|
| 1 | Raw `NaN` in `reminder_channel` is silently treated by the fitted `OneHotEncoder` as an unseen category (all-zero one-hot row) rather than matched to the fitted `"None"` category, producing a materially different, silently-degraded prediction (verified: 0.776 vs 0.789 probability on the same record). Confirmed present in **both** DS candidate pipelines, since they share the same `ColumnTransformer`. Affects 27.3% of the raw dataset (1,366/5,000 rows). | Directly testing both `.joblib` artifacts against real rows with a known-null `reminder_channel`, comparing raw-NaN input vs. explicit `"None"`-string input | **High** — silent, no error/warning, affects over a quarter of records | **Resolved** | `src/models/candidate_models.py::prepare_candidate_input()` added as a mandatory gate before either pipeline is called. Pinned with a parametrized regression test (`tests/test_candidate_models.py::test_raw_nan_reminder_channel_differs_from_prepared_input`) that runs against the live artifacts on every test run. |
| 2 | `distance_to_clinic_km` raw `NaN` — checked for the same class of bug as issue #1, since it's also a column with missing values feeding into the shared preprocessor. | Direct test of a real row with missing `distance_to_clinic_km` through both pipelines | Low (confirmed non-issue) | **Closed — no fix needed** | Bundled `SimpleImputer(strategy="median")` correctly imputes the fitted median (8.6 km). Verified and documented as a contrast case so this column isn't mistakenly "fixed" in a future pass. |
| 3 | DS's Week 6 handoff message described the Week 5 ML Engineering baseline as using a "patient-grouped train/test split" with specific reported metrics (Accuracy 62.4%, ROC-AUC 0.677) — but the actual Week 5 `src/models/train.py::split_data()` uses a plain stratified split, not group-aware, and its own docstring flags this as an unimplemented Week 6 TODO. | Reading the actual Week 5 code (not assuming from the handoff description) and comparing to the handoff's stated numbers | Medium — risk of comparing new results against a baseline that was never actually run | **Open, flagged, not yet resolved** | Does not block the Week 6 candidate-model integration (which is schema/artifact-based, not dependent on the Week 5 baseline's split method). Recommended fix (implementing `GroupShuffleSplit` in the Week 5 baseline) is deferred — see Week 7 Testing Plan, item 5. |
| 4 | Two feature-set schemas now coexist in the repository: the Week 5 baseline's 16-feature schema (`config.ALL_MODEL_FEATURES`, via `feature_engineering.py`) and the Week 6 candidate models' 11-feature schema (`config.CANDIDATE_ALL_FEATURES`). A caller could plausibly pass the wrong schema's fields to the wrong model. | Comparing DS's supplied schema against the existing `config.yaml` feature lists while building `candidate_models.py` | Medium — developer-facing risk, not a runtime silent-failure risk (wrong/missing fields are rejected loudly) | **Mitigated, not eliminated** | `predict()`'s dispatcher routes to model-specific validation (`PredictionInputError` vs `CandidateModelInputError`), so a schema mismatch is always a loud, named error — never silent. Full unification of the two schemas was considered and rejected: DS's models were deliberately trained on a feature subset (see Issue Log context in `reports/week6_model_verification.md`), so forcing one shared schema would misrepresent what each model actually expects. |
| 5 | `predict()`'s dispatcher initially had no logging of its own — `candidate_models.py` logged the null-replacement action, but which model was invoked, and whether a request succeeded or failed, was not recorded anywhere at the dispatcher level. | Re-reading the Week 6 assignment's explicit requirement ("add appropriate logging or execution information") against the actual code | Low — functionality was correct, but not observable/auditable | **Resolved** | Added `logging` calls to `predict()`: logs `model_name` on every request, `label`/`risk_category` on success, and `error_type` (never record contents) on rejection. Verified manually that no patient-relevant fields (age, gender, distance, etc.) appear in the log stream. |
| 6 | The repository's reproducibility claim ("verify the pipeline can be reproduced using the documented setup") had only been checked by re-running code in the same already-configured environment — never validated against a genuinely fresh environment built only from `requirements.txt`. | Re-reading the Week 6 assignment's explicit requirement against what had actually been tested | Medium — an unverified reproducibility claim is not the same as a verified one | **Resolved** | See `reports/week6_reproducibility_check.md` — a fresh virtual environment was built from `requirements.txt` alone and the full test suite + pipeline run against it. |
